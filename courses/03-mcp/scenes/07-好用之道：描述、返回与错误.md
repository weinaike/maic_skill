## 讲稿

同一个功能，两个 MCP，一个模型用得飞起，一个怎么都不被调用——差别往往就在这一页的四个细节上。 @[text_title]

第一个，描述。工具的描述就是写给模型看的提示词：什么时候该用、怎么传参、什么时候不该用，都要写进去。反面例子就一句"检索文献"；正面例子会说清楚"用于按关键词检索学术文献，适合文献调研场景，全文获取请改用下载工具"。记住一句话：工具好不好用，一半取决于描述写得好不好。 @[text_card_desc]

另外提醒一句：一个 Server 别堆太多工具，几十个工具挤在一起，模型会选花眼——这也算上下文管理问题，Token 那一讲讲过的道理在这里同样成立。

第二个，返回。只回模型需要的字段，别把整张表原样丢回去。查文献就回标题、年份、链接，不要把摘要全文、原始 JSON 都塞进去——返回越长，上下文烧得越快，模型还容易看丢重点。 @[text_card_ret]

第三个，错误。出错时抛出的异常信息要"模型可读"：别说"错误 500"，要说"日期格式应为年月日，比如收到的是 2026 年 1 月 3 日"。模型读到有用的错误信息，会自己纠正参数重试，一遍就过。 @[text_card_err]

第四个，Context。给处理函数加一个 ctx 参数，就能用 ctx.info 记日志、report_progress 上报进度——长时间跑批的时候，你能看到它跑到哪了，而不是干等。 @[text_card_ctx]

最后一条安全底线：工具返回的内容，就是模型的输入。来源不明的文本里可能藏着指令，路径参数要校验，密钥永远走环境变量，绝不写进代码。 @[text_secure]
