## 讲稿

Writing the code is only the start. Things refusing to run — that's daily life. This section hands you a debugging playbook. Follow it, and you'll pin down almost every problem within five minutes. @[text_title]

Start with the debugging tools. MCP Inspector is the official debugger. It connects straight to your Server, lets you call each tool by hand, and shows you the raw request and response. That's far faster than blind trial and error inside a client. Add client logs plus stdio log redirection, and whatever your Server prints lands in a file you can read. @[text_test]

Then build the one habit every researcher should have: scripted tests with the Client that ships with fastmcp. No client needs to be open. A single call_tool line verifies what the tool does. Save that as a test script, rerun it after every change, and your acceptance check is reproducible.

The high-frequency pitfalls? Just four. The first two: a loose schema, so the model invents arguments — strict types block that, as Section Five covered. And oversized returns — that's the lean-return lesson from Section Seven. @[text_pit_schema]

The other two. Paths and dependencies that don't match: your Server runs as a child process. Its working directory and virtualenv are often not what you expect. And unconfirmed side effects: for actions that delete files or overwrite data, always spell out the consequences in the description. @[text_pit_env]

So when something does break, how do you track it down? Walk this path. Can't connect? Check the config and the process — is the command right, did the Server even start? Connected but never called? Check the description — the model doesn't know when it should reach for the tool. @[text_path]

Called, but the results look weird? Check the return — is the format right, did it get truncated for length? Three symptoms, three directions. No random guessing required.

Finally, how you ship it. For local, personal use, stdio is enough. Want others in the lab to connect too? Then call mcp.run with transport set to http, and spin up a remote server. Get it running smoothly on stdio first, then decide whether to go remote. Next up: three questions to check how well you've absorbed all this.
