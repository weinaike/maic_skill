## 讲稿

Same feature, two MCPs: the model hammers one and never touches the other; the difference usually comes down to the four details on this page. @[text_title]

Detail one, the description. A tool description is a prompt written for the model: when to use it, how to pass arguments, when not to. All of that belongs in there. The bad one is a bare "search papers"; the good one says "keyword search over academic literature, built for survey work; use the download tool for full text". @[text_card_desc]

Remember one line: half of what makes a tool usable is a well-written description. @[text_sub]

One more caution: don't pile too many tools onto one Server; a few dozen crammed together and the model gets choice paralysis. That's a context-management problem too, and the lesson from the Token lecture holds here just the same.

Detail two, the return. Return only the fields the model needs; never dump the whole table back raw. A literature search should return title, year, and link, not the full abstract and the raw JSON. The longer the return, the faster the context burns, and the more easily the model loses the point. @[text_card_ret]

Detail three, errors. When a call fails, the exception you raise has to be readable by the model. Don't say "error 500"; say "the date format should be year, month, day; I received January 3rd, 2026". Given a useful error, the model corrects its arguments and retries, getting it right in one pass. @[text_card_err]

Detail four, Context. Add a ctx parameter to your handler, and you gain ctx.info for logging and report_progress for progress. During a long batch run you can see where it is, instead of waiting in the dark. @[text_card_ctx]

One last line of defense: whatever a tool returns becomes the model's input. Text from unknown sources may hide instructions; validate path parameters; keep keys in environment variables, never in code. @[text_secure]
